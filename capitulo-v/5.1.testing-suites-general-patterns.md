### ***5.1. Testing Suites & General Patterns*** {#5.1.-testing-suites-&-general-patterns}

El ecosistema de DriveOS, desarrollado por ForkDevs, sigue los principios de Domain-Driven Design con arquitectura hexagonal, persistencia políglota, mensajería asíncrona por Kafka y un API Gateway de alto desempeño en el borde. En un sistema distribuido, multi-tenant, con componentes de tiempo real y obligaciones tributarias, validar solo los controladores REST no alcanza. Hay que cubrir tanto la lógica de dominio como las integraciones entre microservicios, bases de datos y servicios externos.  
Para sostener la confiabilidad del sistema bajo alta concurrencia de telemetría IoT vehicular y operaciones de taller simultáneas, se definió un conjunto de herramientas de testing para cada stack del ecosistema:  
*Java 21+ / Spring Boot (microservicios transaccionales core)*  
JUnit 5 es el motor de ejecución principal. Mockito y AssertJ cubren las pruebas unitarias de entidades de dominio, Value Objects y casos de uso con aislamiento estricto. Testcontainers levanta contenedores Docker efímeros durante el pipeline CI/CD para validar integraciones con PostgreSQL y Kafka. ArchUnit verifica automáticamente las reglas de arquitectura y el desacoplamiento de capas DDD.  
*Go / Fiber (API Gateway y captura de telemetría en el borde)*  
El paquete testing de Go, junto con Testify (assert y require), cubre el enrutamiento de peticiones, la validación de tokens JWT con RS256, la inyección de contexto multi-tenant y el rate limiting. httptest simula peticiones HTTP entrantes sin levantar servidores reales. GoMock aísla las dependencias de red y caché con Redis.  
*Python / FastAPI (procesador IoT y motor de reglas analíticas)*  
Pytest con pytest-asyncio y el AsyncClient de HTTPX prueba el motor de detección de anomalías y la evaluación de códigos DTC y parámetros PID de telemetría OBD-II. Los fixtures asíncronos simulan flujos desde tópicos de Kafka y miden la latencia del motor de reglas bajo cargas sintéticas controladas.
