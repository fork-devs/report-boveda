### ***5.2.2 Source Code Management*** {#5.2.2-source-code-management}

El código fuente del ecosistema DriveOS Workshop se gestiona de forma centralizada bajo la organización oficial en GitHub: https\://github.com/fork-devs. La arquitectura del repositorio refleja la modularidad del sistema y la separación entre aplicaciones cliente, plataforma de microservicios y librerías transversales:

**driveos-platform (Privado):**  Repositorio central multi-módulo Maven que aloja los microservicios backend autónomos ('api-gateway', 'iam-service', 'billing-service', 'iot-service', 'operations-service', 'inventory-service', 'core-service', 'fleet-service') y las bibliotecas de dominio ('shared-kernel', 'auth').

**driveos-web (Público):**  Repositorio que aloja la aplicación web y móvil para gestión de taller y técnicos mecánicos, desarrollada con Angular 21, Phosphor Icons y [Three.js](http://Three.js).

**erp-integration-hub (Público):**  Repositorio del microservicio en Java que encapsula la Capa Anticorrupción (ACL) para las integraciones con SUNAT, pasarela de pagos Stripe y consultas vehiculares RENIEC/SUNARP.

**erp-api-gateway, erp-auth-service, erp-tenant-service (Públicos):**  Repositorios desacoplados que contienen las implementaciones especializadas de seguridad perimetral, servidor de autorización OIDC con claves públicas JWKS y gestión de organizaciones.

**upc-pre-202602-si657--16723--ForkDevs-performance-report (Público):**  Repositorio de control institucional que aloja los informes de participación del equipo y la documentación del proyecto.

**1\. Flujo de Trabajo de Ramas: GitFlow**

El equipo implementa rigurosamente el modelo GitFlow (Driessen, 2010\) para coordinar el trabajo paralelo de los cinco integrantes sin generar conflictos en producción:

**• main:**  Rama de código productivo, estable y desplegable. Solo recibe fusiones probadas provenientes de ramas 'release/' o 'hotfix/'.

**• develop:**  Rama de integración continua donde se consolidan las funcionalidades terminadas del sprint. Es la base de trabajo para las nuevas ramas de características.

**• feature/\*:**  Ramas creadas a partir de develop para desarrollar tareas específicas de una User Story. Convención de nomenclatura: 'feature/USXX-nombre-breve' (ejemplos reales en los repositorios: 'feature/real-api' en driveos-web, 'feature/runtime-and-contract' en driveos-platform, 'feature/US23-iam-rbac'). Al concluirse, se integran mediante Pull Request con revisión obligatoria por pares.

**• release/\*:**  Ramas destinadas a la estabilización de versiones previas a la entrega de sprint. Nomenclatura: 'release/v1.0.0-sprint.1'.

**• hotfix/\*:**  Ramas para corrección urgente de fallas detectadas en main. Nomenclatura: 'hotfix/v1.0.1-patch'.

**2\. Versionamiento Semántico (Semantic Versioning 2.0.0)**

Se adopta el estándar SemVer 2.0.0 (Preston-Werner, 2013\) bajo la estructura X.Y.Z (MAJOR.MINOR.PATCH):

**• MAJOR (X):**  Se incrementa ante cambios incompatibles en los contratos públicos REST o esquemas de eventos (ejemplo: modificación de campos obligatorios en el API Gateway).

**• MINOR (Y):**  Se incrementa al añadir nuevas funcionalidades compatibles hacia atrás (ejemplo: nuevo endpoint de consulta de órdenes).

**• PATCH (Z):**  Se incrementa ante correcciones de errores, ajustes de dependencias o refactorizaciones internas.

**• Tag Hito TP1:**  Para la entrega del Trabajo Parcial (Sprint 1), la versión oficial del release se etiqueta como 'v1.0.0-sprint.1'.

**3\. Convenciones de Mensajes de Commit: Conventional Commits**

Los mensajes de confirmación siguen el estándar Conventional Commits v1.0.0 bajo la estructura '\<tipo\>(\<alcance\>): \<descripción imperativa en inglés\> \[US-XX\]':

**• Tipos obligatorios:**  feat: Nuevas funcionalidades (ejemplo: 'feat(iam): implement jwt authentication and rbac verification \[US23\]').

fix: Corrección de defectos (ejemplo: 'fix(operations): prevent invalid state transitions in work order \[US03\]').

test: Adición de pruebas unitarias o de integración (ejemplo: 'test(gateway): add token bucket rate limiter tests').

refactor: Mejoras estructurales sin alterar funcionalidad (ejemplo: 'refactor(shared): extract Money and Result to shared-kernel').

docs: Actualización de contratos OpenAPI o documentación técnica (ejemplo: 'docs(openapi): document work order endpoints \[US02\]').
