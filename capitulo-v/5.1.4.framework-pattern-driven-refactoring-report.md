### ***5.1.4. Framework Pattern Driven Refactoring Report*** {#5.1.4.-framework-pattern-driven-refactoring-report}

Como parte del proceso de mantenimiento evolutivo e ingeniería de software rigurosa, se ejecutó un proceso sistemático de Refactorización Dirigida por Patrones del Framework (Framework Pattern Driven Refactoring). Esta práctica consistió en identificar deudas técnicas, cuellos de botella y "olores de código" (code smells) acumulados durante las fases iniciales de prototipado para transformarlos en implementaciones robustas fundamentadas en patrones DDD y microservicios resilientes.  
El informe de refactorización registra los siguientes hitos de transformación arquitectónica:

* • Desacoplamiento de Controladores y Eliminación del "Anemic Domain Model": En la versión inicial, la lógica de negocio (como el cálculo de márgenes y asignación de técnicos) residía en servicios anémicos y controladores sobredimensionados (Fat Controllers). Se refactoriza extrayendo dicha lógica hacia las entidades ricas del dominio (Work Order, Service Task), encapsulando el comportamiento en métodos de dominio expresivos y utilizando Value Objects inmutables para validar reglas en el momento de la instancia.  
* Transición de Comunicación Sincrónica Bloqueante a Eventos con Outbox: Originalmente, al liquidar una orden de trabajo, el Work Order Service realizaba llamadas HTTP REST sincrónicas encadenadas hacia el InventoryService y el Billing Service. Ante fallos de red o caídas temporales, la transacción se aborta de manera inconsistente. Se refactoriza implementando el patrón Transactional Outbox y eventos asíncronos en Kafka, reduciendo el tiempo de respuesta del endpoint de liquidación de 1,850 ms a menos de 120 ms.  
* Encapsulación de Integraciones Fiscales mediante Capa Anticorrupción (ACL): Se detectó que el modelo JSON propietario del proveedor de facturación electrónica (Nube Fact) comenzaba a filtrarse hacia las entidades del núcleo del taller. Se refactoriza aplicando una Capa Anticorrupción (ACL) y el patrón Adaptador (Nube fact Adapter), aislando el modelo interno de comprobantes mediante el puerto Emisor Tributario Port. Esto permite desacoplar totalmente la lógica tributaria peruana de la lógica operativa de la orden de trabajo.  
* Optimización del Algoritmo de Costeo FIFO con Bloqueo Optimista: Se refactoriza el motor de descuento de stock de repuestos en el InventoryService. La consulta original con bloqueo pesimista a nivel de tabla provocaba cuellos de botella (deadlocks) ante despachos simultáneos en bahías de servicio. Se rediseñó el algoritmo particionando el Kardex por lotes de compra con control de versiones (@Version en JPA / Optimistic Locking), multiplicando por 4 el rendimiento transaccional de consumo de repuestos concurrentes.  
* Garantía de No-Regresión mediante Pipeline Automatizado de CI/CD: Cada una de las refactorizaciones fue respaldada por las suites de pruebas automatizadas (JUnit 5, Testcontainers y GitHub Actions). El pipeline de integración continua ejecutó más de 180 pruebas unitarias y de integración en cada Pull Request, garantizando una tasa de cero regresiones funcionales y elevando la cobertura de código del proyecto del 62% inicial a más del 87% consolidado.
