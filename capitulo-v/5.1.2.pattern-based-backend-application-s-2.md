### ***5.1.2. Pattern Based Backend Application(s)*** {#5.1.2.-pattern-based-backend-application(s)-1}

Las aplicaciones backend de DriveOS están diseñadas e implementadas sobre un sólido marco de patrones arquitectónicos y de diseño empresarial. La suite de pruebas no solo válida la corrección sintáctica y funcional del código, sino que verifica sistemáticamente la adherencia arquitectónica a los patrones adoptados:  
Domain-Driven Design (DDD) y Arquitectura Hexagonal (Puertos y Adaptadores): Organiza el código en capas concéntricas estrictamente desacopladas: Dominio (Domain), Aplicación (Application) e Infraestructura (Infrastructure). Mediante pruebas automatizadas con Arch Unit en Java, se imponen reglas arquitectónicas en tiempo de compilación/testing para asegurar que la capa de Dominio no dependa de ninguna librería de base de datos (Spring Data / JPA) ni de infraestructura web. Los puertos de salida (como Repositorio Orden sPort o Emisor Tributario Port) se verifican mediante contratos de interfaz rigurosamente probados con adaptadores simulados (Mock Adapters) y adaptadores reales (Postgres Adapter, Nube factAdapter).  
Arquitectura Dirigida por Eventos (Event-Driven Architecture) con Apache Kafka: Permite el desacoplamiento temporal y espacial entre contextos delimitados. Los eventos de dominio (como Orden Liquidada Event, Lectura Telemétrica Capturada Event) son publicados en tópicos particionados. Las pruebas de integración con Tests Containers Kafka verifican la serialización/deserialización binaria bajo especificación Cloud Events, garantizando que los consumidores procesan mensajes respetando el orden por tenant\_id o vehiculo \_id.  
Patrón Transactional Outbox y Outbox Relay: Garantiza la consistencia atómica entre el guardado de la entidad en la base de datos relacional y la publicación del evento en Kafka, evitando el problema de doble escritura distribuida. Las pruebas de integración validan que el comando de negocio inserte simultáneamente la orden y el registro en la tabla outbox events dentro de la misma transacción ACID de PostgreSQL. El worker Outbox Relay es probado bajo condiciones de fallo de red en Kafka, verificando que los mensajes permanezcan en estado PENDING y se reinventen sin pérdida de datos.  
Patrón Saga Coreografiada para Procesos Distribuidos: Modela flujos transaccionales entre múltiples microservicios (por ejemplo: Liquidar Orden a Reservar Stock FIFO a Emitir Factura SUNAT) sin transacciones distribuidas bloqueantes (2PC). La suite de pruebas automatizadas simula escenarios de éxito y flujos de compensación (Rollback asíncrono / Compensating Transactions), verificando que si la emisión tributaria es rechazada por SUNAT, se dispare un evento Facturación Rechazada Event que libere inmediatamente el inventario reservado en el Inventory Service.  
Patrón Circuit Breaker y Degradación Elegante (Resilience 4j): Protege al sistema ante caídas o latencias excesivas en APIs externas gubernamentales o de terceros (SUNAT, Nube Fact, RENIEC). Utilizando WireMock, se inyectan tasas de error HTTP 500 y tiempos de espera superiores a 5 segundos para verificar que el Circuit Breaker transición automáticamente de CLOSED a OPEN, redirigiendo las peticiones a métodos Fallback que encolan la facturación en modo pendiente para posterior emisión sin interrumpir la entrega física del vehículo en el taller.  
Patrón CQRS (Command Query Responsibility Segregation): Separa de forma explícita las operaciones de escritura transaccional (comandos en PostgreSQL optimizados para consistencia ACID) de las consultas y tableros analíticos de lectura (modelos de lectura optimizados con vistas materializadas y Redis Caching). Se valida que los tiempos de respuesta de consulta de órdenes e indicadores KPI se mantengan en menos de 300 ms incluso ante altas tasas de inserción concurrente.  
Patrón Multi-Tenancy con Row-Level Security (RLS) y Context Propagation: Garantiza el aislamiento absoluto de los datos entre diferentes talleres mecánicos que comparten la misma infraestructura de base de datos. Se han implementado pruebas de penetración y regresión automatizadas que inyectan tokens con tenant\_id cruzados, verificando que el middleware del API Gateway y las políticas RLS en PostgreSQL bloqueen cualquier acceso no autorizado devolviendo respuestas HTTP 403 Forbidden to result sets vacíos.
